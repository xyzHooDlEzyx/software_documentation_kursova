# Специфікація вимог: фітнес-додаток, варіант 4

## 1. Призначення, статус і джерела

Документ визначає перевірювані вимоги до курсового веб-додатка до проєктування UML, БД та REST API. `CONFIRMED` означає пряму вимогу методички або явне рішення в поточному завданні; `PROPOSED` — рекомендовану конкретизацію; `OPEN` — вибір, що потребує рішення; `CONFLICT` — несумісні джерела. Пріоритет `Must` не перетворює запропонований спосіб реалізації на вимогу методички.

Джерела: **M1** — `docs/kursova_DPZSP.pdf`, §1; **M4** — там само, §2 «Проєкт 4»; **M3** — там само, §3; **P** — `docs/PLAN_VARIANT_4.md`; **T** — завдання з аналізу вимог; **S** — `.agents/skills/fitness-requirements/SKILL.md`; **D-2026-10-27** — прямі рішення користувача від 27.10.2026 у цьому чаті; **D-2026-10-28** — підтверджені рішення щодо BR-006/007, мінімуму фактичних вправ, пріоритету причин kcal, політики архівації MVP та BR-032 від 28.10.2026; **D-2026-10-31** — явне погодження власником AR-01–AR-04: закриття після скасування, джерело й час персонального складу, active-only E01 та обмеження архівації draft; **C2024** — локальна копія `docs/1_2024-adult-compendium_1_2024.pdf` (2024 Adult Compendium of Physical Activities, таблиця кодів активностей і MET). У репозиторії немає моделей, API, архітектурних ADR чи реалізації. План містить пропозиції `[Рішення]`, а не підтвердження їхнього окремого погодження. Там, де T прямо називає попередньо обрані параметри нагадувань, їх прийнято як підтверджені для цього аналізу.

Методичка вимагає: реєстрацію та профіль (стать, вік, вага, зріст), бібліотеку тренувань, індивідуальні програми, статистику калорій/вправ/ваги, нагадування, досягнення/рейтинги/челенджі, три звіти, БД, REST, користувацький веб-інтерфейс, Use Cases, UML класів, застосовані GoF-патерни, GitHub з історією комітів і звіт за §3. Адмін-частину методичка **пропонує продумати**, але прямо не зобов'язує. Мобільний клієнт не потрібен, якщо реалізовано веб-клієнт.

## 2. Огляд і актори

`Guest` реєструється та входить. `User` керує лише власними приватними даними, користується бібліотекою й соціальними функціями. `Administrator` керує спільним каталогом та конфігурацією, бачить агреговані звіти. Це бізнес-роль через Django Group/Permissions (`is_staff=True`, `is_superuser=False`); технічний superuser є окремим службовим обліковим записом. `System` виконує детерміновані перевірки після завершення заняття та показує нагадування; це внутрішній компонент, а не облікова роль. Автентифікація встановлює особу; авторизація перевіряє роль і власника **на кожному запиті та об'єкті**.

### Погоджені поля профілю (OQ-05, D-2026-10-27)

| Поле | Тип | Валідація |
|---|---|---|
| `date_of_birth` | `DateField` | Обчислений вік на локальну дату `Europe/Kyiv` під час першого створення профілю — 19–59 років включно; подальше виправлення дати перевіряють відносно цієї дати створення; `age` не зберігається окремо. |
| `weight_kg` | `DecimalField` | 20.0–500.0 kg включно, один десятковий знак; зміна створює `WeightEntry`. |
| `height_cm` | `DecimalField` | 100.0–250.0 cm включно, один десятковий знак. |
| `gender` | `CharField` | `male`, `female`, `other`, `prefer_not_to_say`. |
| `fitness_goal` | `CharField` | `weight_loss`, `muscle_gain`, `maintenance`. |
| `experience_level` | `CharField` | `beginner`, `intermediate`, `advanced`. |
| `workouts_per_week` | `PositiveSmallIntegerField` | Ціле від 1 до 7 включно. |

`WeightEntry` є джерелом датованої історії ваги; поточне `Profile.weight_kg` не замінює її. Значення ваги в історії також має один десятковий знак і межі 20.0–500.0 kg. Якщо профільну вагу задають уперше чи змінюють, запис ваги створюється разом з оновленням профілю. Точна дата народження і похідний вік приватні. Межу віку 19–59 узгоджено з обраним довідником MET C2024; після 60 років вже зареєстрований User зберігає повний функціонал, крім MET-оцінки нових тренувань (OQ-11).

## 5. Матриця доступу

`R/C/U/D` — читати/створювати/оновлювати/видаляти; `own` — лише власне; `A` — лише бізнес-роль Administrator; `—` — заборонено. Технічний Django superuser не є колонкою цієї матриці й не використовується як звичайний Administrator. Для історичних фактів D означає лише виняткове остаточне видалення всього акаунта за BR-032, не звичайний CRUD; у MVP ця операція не реалізується. Для звітів R не дає доступу до сирих чужих записів.

| Сутність | Guest | User | Administrator |
|---|---|---|---|
| Account/Profile | C власний акаунт | R/U own, зокрема власні псевдонім та opt-in; D — | R стану й U деактивації лише через обмежений admin-екран/дію; загальна зміна User і приватний Profile — |
| WeightEntry | — | R/C/U own; D — | — |
| Exercise/Workout/Category | R опублікованих (PROPOSED) | R опублікованих | R/C/U; D архівація |
| ProgramTemplate | — | R опублікованих; C/U/D — | R/C/U через Django Admin; D лише архівація використаного шаблону |
| UserProgram | — | R/C/U own; D архівація own `draft`/`completed` | —; архівація `active` і відновлення архівного екземпляра поза MVP; спільний шаблон не дає доступу до чужої копії |
| ScheduledSession | — | R/C/U own; D скасування own | — |
| CompletedSession/ExerciseResult | — | R/C own; U/D — | — |

Усі не перелічені операції заборонені. Остаточне видалення акаунта за FR-041 після MVP потребує окремого явно визначеного права й не випливає зі звичайних прав Administrator у цій матриці. Прямий запит з ID чужої сутності відхиляється однаково, незалежно від того, чи ID існує; конкретний код `403`/`404` узгодити в API-контракті. Публічність бібліотеки й псевдонімів — запропоновані рішення, не право на приватні дані.
