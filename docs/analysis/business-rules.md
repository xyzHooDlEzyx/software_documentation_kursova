# Бізнес-правила фітнес-додатка

## 1. Призначення та правила читання

Цей документ конкретизує `requirements.md` для UML, ERD, REST і тестів. Статуси: `CONFIRMED` — пряма вимога методички або явний вибір користувача; `PROPOSED` — рекомендоване правило, яке ще потребує погодження; `OPEN` — без рішення; `CONFLICT` — суперечливі джерела. Методичка `docs/kursova_DPZSP.pdf`, §2 «Проєкт 4», задає **функції**, але майже не задає формул, числових порогів або життєвих циклів. Тому формули нижче не приписуються методичці. Джерела скорочено як M4, P, T, S, D-2026-10-27, D-2026-10-28 і C2024 відповідно до `requirements.md`.

## 2. Терміни та межі даних

| Термін | Визначення |
|---|---|
| `Exercise` | Повторно використовуване визначення вправи з категорією та допустимими параметрами. Не є фактом виконання. |
| `Workout` | Шаблон тренування: впорядкований набір `Exercise` з рекомендованими параметрами. Це одиниця бібліотеки та рейтингу популярності. |
| `ProgramTemplate` | Спільний шаблон програми, який Administrator підтримує в Django Admin; початковий каталог створює Django management command. Використаний шаблон архівують, не видаляють фізично. |
| `UserProgram` | Незалежний екземпляр програми одного User, створений копіюванням `ProgramTemplate`; власник змінює вправи, підходи та розклад. Зміни шаблону не змінюють копію. У попередніх документах називався `TrainingProgram`. |
| `ScheduledSession` | Намір виконати один `Workout` у запланований момент, можливо в рамках програми; має життєвий стан. |
| `CompletedSession` | Незмінний факт одного завершення з фактичним часом, тривалістю, snapshot шаблону/ваги/MET і оцінкою kcal. Є джерелом статистики. |
| `ExerciseResult` | Фактичний результат конкретної вправи в `CompletedSession`; відсутня або пропущена вправа не рахується виконаною. |
| `WeightEntry` | Датований вимір маси, незалежний від поточного значення профілю. |
| `PointTransaction` | Незмінний запис нарахування балів з унікальним джерелом, типом і UTC-часом; єдине авторитетне джерело Activity Points. |

Конкретні пріоритети кількох шаблонів наведено в розділі 10; за відсутності збігу — явне повідомлення. AI/ML не застосовуються. Кілька активних програм допустимі за попередньою пропозицією S. | FR-011–014/038 |
| BR-006; CONFIRMED щодо поточного прогресу, snapshot і замороженого порогу бонусу (OQ-12, D-2026-10-28) | Новий `UserProgram` спочатку має стан `draft`; після налаштування щонайменше одного слота User активує його (`active`). Активний `UserProgram` редагується без версій набору слотів. **Поточний** прогрес: `100 × completed_planned / total_planned`, де знаменник — поточні нескасовані `ScheduledSession` цієї програми (включно з missed), чисельник — серед них слоти з одним `CompletedSession`. Скасування незавершеного слота зменшує знаменник; перенесення того самого слота його не змінює; додавання слота збільшує знаменник і може зменшити поточний відсоток. Якщо знаменник 0, прогрес 0%; показ до 1 десяткового знака. Проміжні значення не зберігаються й не відтворюються. Відсоток є інформаційним показником і сам по собі не надає права на бонус BR-007. При активації фіксується `bonus_target_sessions = max(3, initial_planned_sessions)`, де `initial_planned_sessions` — кількість нескасованих слотів на цей момент; подальше скасування не зменшує поріг. Поріг стосується лише бонусу, а не права створити чи завершити коротку програму. Лише при завершенні записується snapshot підсумку в `UserProgram`: `completed_at`, `total_planned_at_completion`, `completed_planned_at_completion`, `progress_percent_at_completion`. Незмінні `CompletedSession` зберігаються окремо. | FR-015/017, UC-009 |
| BR-007; CONFIRMED щодо критерію закриття, окремого порогу та одноразового бонусу (D-2026-10-28) | `UserProgram` завершується, коли `total_planned>0` і всі його поточні нескасовані слоти завершено; підсумковий snapshot зберігають незалежно від балів. **Право на +50** виникає лише в момент цього завершення, якщо кількість завершених планових слотів екземпляра досягла незмінного `bonus_target_sessions` BR-006. Самі `100.0%` прогресу не достатні для бонусу. Якщо поріг не досягнуто, програма завершується без +50; після закриття її не можна доповнити заняттями заради бонусу. За виконання порогу в тій самій атомарній операції нараховують +50 один раз за конкретний `UserProgram`. У відповіді API `status=completed` і `bonus_earned` відображаються окремо; `bonus_earned` обчислюється за наявністю `PointTransaction` бонусу, а не зберігається другим джерелом істини. UI показує завершення програми окремо від повідомлення про нарахування +50. Після завершення екземпляр закритий для змін; повторне проходження того самого `ProgramTemplate` створює новий `UserProgram` із власним можливим бонусом. | FR-016/030 |
| BR-008; PROPOSED | `ScheduledSession`: `planned`, `completed`, `cancelled`, `missed` (останнє — похідний стан після планового часу, без автоматичного завершення). Перенесення `planned`/`missed` зберігає ID та історію зміни часу. Для MVP прийнято легкий `reschedule_history JSONB` зі списком попередніх UTC-часів; це прикладна історія, не захищений від підробки аудит, окрема таблиця не потрібна. `completed` не переноситься. `cancelled` не завершується; для нового наміру створюється новий слот. | FR-017 |
| BR-009; CONFIRMED | Зміна `ProgramTemplate` не змінює жодного раніше створеного `UserProgram`; зміна активного `UserProgram` впливає лише на поточні/майбутні планові слоти. Факти `CompletedSession`, `ExerciseResult`, snapshots калорій, бали та вже отримані досягнення не змінюються після правок профілю/програми. Історичні проміжні відсотки прогресу не відтворюються; зберігається тільки підсумковий snapshot завершення BR-006. | FR-011/012/015/022 |
| BR-010; CONFIRMED щодо мінімум одного фактичного результату, PROPOSED щодо інших деталей | Завершення приймає фактичні результати та додатну тривалість у хвилинах. `WorkoutCompletionService` до запису факту вимагає щонайменше один валідний, реально виконаний `ExerciseResult` для планового й позапланового завершення: пропущені вправи не рахуються, усі планові вправи виконувати не обов’язково; нуль результатів відхиляє завершення без балів. Один `ScheduledSession` має не більше одного `CompletedSession`; позапланове виконання має окремий ключ і не дає бонус за плановий день. Успішна операція атомарно створює факт, результати, kcal snapshot, основні `PointTransaction` і змінює стан слота. Повтор із тим самим ключем повертає попередній результат. | FR-018–021/030, UC-006/007 |

**Архівація `UserProgram` для MVP — CONFIRMED (D-2026-10-28).** Стан життєвого циклу має значення `draft`, `active` або `completed`; `is_archived` є окремим прапорцем. Можна архівувати лише `draft` та `completed`, повторний запит ідемпотентний. Архівація завершеної програми не змінює підсумковий snapshot, `CompletedSession`, `ExerciseResult` чи `PointTransaction` і не нараховує бонус вдруге. Архівація `active` та відновлення архівного екземпляра не підтримуються в MVP; їхня майбутня політика слотів і нагадувань є **OUT OF SCOPE / FUTURE DECISION**.

### Приклад прогресу

В активному `UserProgram` є 5 слотів: 2 завершені, 1 пропущений, 1 перенесений, 1 скасований до початку. Поточний знаменник 4, чисельник 2, прогрес `50.0%`. Якщо додати новий слот, поточний знаменник стає 5 і прогрес `40.0%`; попередні `50.0%` не зберігаються. Якщо при активації було 5 слотів, `bonus_target_sessions=5`. Після скасування одного з них завершення решти чотирьох дає `4/4 = 100.0%`: програма закривається зі snapshot **без** +50. Щоб отримати бонус, треба додати замінний слот **до завершення останнього поточного** заняття та завершити всі 5. Для програми з одним слотом `bonus_target_sessions=3`; після одного завершення вона закривається без +50. Спрощену модель без проміжних версій підтверджено OQ-12; конкретний поріг бонусу підтверджено D-2026-10-28. Для 3/3 при початковому порозі 3 і 5/5 при порозі 5 програма закривається з +50; за нульового нескасованого плану не закривається.

## 4. Калорії

| ID; статус | Правило | Пов'язано |
|---|---|---|
| BR-011; PROPOSED | Оцінка: `kcal = Σ(MET_i × weight_kg × duration_i_hours)`. MET безрозмірний, вага в kg, час у годинах, результат — орієнтовні kcal. Якщо вправи не мають окремого часу, можна використати **лише явно зіставлений із довідником** MET для всього Workout; за його відсутності kcal невідомі. Загальну тривалість не множити на MET кожної вправи. | FR-021, UC-006 |
| BR-012; CONFIRMED щодо джерела ваги й відсутньої оцінки kcal | Вагу для історичного розрахунку брати **лише** з останнього `WeightEntry` з timestamp ≤ часу завершення; поточне `Profile.weight_kg` не підставляти замість відсутньої історії. Перший запис профільної ваги має створити `WeightEntry` за BR-001. Фактична тривалість обов'язкова й додатна. У `CompletedSession` зберігати snapshot ваги з виміру, MET/версії довідника, тривалості та kcal. Якщо оцінка неможлива, `estimated_calories=null`; невідоме не підмінювати 0. Причину обирають у визначеному після BR-013 порядку, зокрема `missing_weight` перед `missing_met`, коли обидва входи відсутні. Завершення дозволене без оцінки, щоб не втратити валідний факт виконаних вправ. | FR-004/021 |
| BR-013; CONFIRMED щодо джерела й вікової сфери, PROPOSED щодо зберігання | Довідкове джерело MET — локальна копія C2024: [`docs/1_2024-adult-compendium_1_2024.pdf`](../1_2024-adult-compendium_1_2024.pdf), [офіційна сторінка](https://pacompendium.com/adult-compendium/). PDF містить колонки `Major Heading`, `Activity Code`, `MET Value`, `Activity Description`; зіставлення вправи слід робити за **описом конкретної активності та інтенсивності**, а не лише за широкою категорією cardio/strength/yoga. Довідник призначено для дорослих 19–59 років, що відповідає погодженій межі нового профілю. `Exercise.met_value` може бути `null`, якщо відповідного коефіцієнта немає; зберігати також 5-значний `Activity Code` і версію C2024, щоб вибір було відтворено. Якщо на локальну дату завершення в `Europe/Kyiv` вже зареєстрований User має 60 років або більше, він зберігає весь функціонал, але C2024 не застосовують для оцінки цього заняття: `estimated_calories=null` з причиною `unsupported_age_for_reference`, історичні kcal не змінюються. `duration_i` додатна, сума сегментів ≤ фактичної тривалості; незаповнений залишок оцінювати лише за наявності зіставленого MET Workout, інакше kcal лишаються `null`. Розрахунок десятковий, до `0.01 kcal`, `half-up`; історичні оцінки не перераховуються. | FR-020/021 |

Для 70 kg, MET 6, 30 хв: `6 × 70 × 0.5 = 210.00 kcal`. Для 20 хв MET 6 і 10 хв MET 3: `6×70×20/60 + 3×70×10/60 = 175.00 kcal`. Це **оцінка**, не вимір. Для strength/cardio/yoga достатньо одного розрахункового сервісу з різними MET; `Strategy` потрібна лише за реально різних алгоритмів, яких джерела не вимагають.

**Пріоритет причини відсутньої оцінки (D-2026-10-28):** спершу перевірити вік на локальну дату завершення: якщо User має 60+ років, `unsupported_age_for_reference`; інакше перевірити останній придатний історичний `WeightEntry`: за його відсутності `missing_weight`; інакше перевірити достатність застосовних MET для повної оцінки: за нестачі `missing_met`. У всіх трьох випадках `estimated_calories=NULL`, не 0. Формула BR-011, вибір ваги BR-012, точність і округлення BR-013 не змінюються.

### BR-032: вимоги до зв’язків і перевірки видалення

Для ERD кожна персональна сутність повинна належати User без неоднозначності. Прямі зв’язки власності `Profile.user`, `WeightEntry.user`, `UserProgram.user`, `ScheduledSession.user`, `CompletedSession.user`, `Notification.user`, `PointTransaction.user`, `UserAchievement.user` і `ChallengeParticipation.user` проєктувати з `on_delete=CASCADE`; `ExerciseResult` видаляється через `CompletedSession` з `on_delete=CASCADE`. Персональні соціальні зв’язки мають зникати при видаленні будь-якого залученого User. Зв’язки персональних записів зі спільними `ProgramTemplate`, `Workout`, `Exercise`, `Achievement` і `Challenge` можуть використовувати `PROTECT` або іншу відповідну політику: вона запобігає випадковому видаленню спільної сутності, на яку є посилання. Видалення персонального запису, який **посилається** на каталог, не повинно видаляти сам каталог; якщо каталог використано, його архівують за BR-003. Якщо конкретна персональна сутність отримує непрямий шлях каскаду, потрібно перевірити, що він справді видаляє її при `User.delete()` і не лишає сиріт.

Між персональними сутностями допустимі `PROTECT` або `SET_NULL` для захисту історії під час звичайних операцій, **лише якщо вони не порушують повне очищення при видаленні User**. `PROTECT` може зупинити каскад через `ProtectedError`; `SET_NULL` можливий лише для nullable зв’язку і сам по собі не видаляє залежний запис. Тому для зв’язку з `PROTECT` потрібне явне очищення/розв’язання залежності в тій самій атомарній процедурі перед `User.delete()`, або інший тип зв’язку, що не блокує видалення. Для запису з `SET_NULL` має існувати інший каскадний шлях власності від User. Це необхідно підтвердити інтеграційною перевіркою на PostgreSQL, а не припускати з самої схеми. [Django `ForeignKey.on_delete`](https://docs.djangoproject.com/en/5.2/ref/models/fields/#django.db.models.ForeignKey.on_delete) описує `CASCADE`, `PROTECT` і `SET_NULL` як поведінку ORM.

Критерії приймання наступного етапу: після авторизованого видалення жодного персонального запису цього User не лишилося, спільні каталоги та визначення збережені й доступні іншим, а особисті записи другого User, який користувався тими самими каталогами, не змінилися; зв’язки між видаленим і другим User прибрані, рейтинг не містить видаленого User, звіти перераховані; збій будь-якого кроку відкочує всю операцію. Окремо перевірити, що деактивація нічого не видаляє, а звичайний API не дозволяє видалити одиничний `CompletedSession`. У MVP реалізують лише деактивацію; її інтерфейс не називає цю дію видаленням. До публічного використання потрібно окремо визначити спосіб обробки резервних копій і журналів та повний операційний порядок видалення згідно із [законодавством про персональні дані](https://zakon.rada.gov.ua/laws/show/2297-17#Text).

### Межі транзакції та сценарії помилок

Помилка в будь-якому обов'язковому кроці BR-030 скасовує всю операцію. Відсутня оцінка kcal за BR-012 не є помилкою створення факту, якщо решта обов'язкових полів валідні. Успіх повертає той самий результат при повторі ключа. Конфлікт двох одночасних завершень одного слота вирішується унікальністю `scheduled_session_id` і транзакцією: один факт, другий запит отримує вже створений результат або контрольовану помилку конфлікту. Якщо одночасно завершуються різні слоти одного `UserProgram`, блокування його рядка серіалізує перевірку `bonus_target_sessions` та закриття; другий запит перечитує стан після першого, а унікальна транзакція бонусу додатково гарантує не більше одного +50. Якщо звіт запитано під час завершення, він може бачити стан до або після коміту, але не часткові дані. [Django QuerySet API](https://docs.djangoproject.com/en/5.2/ref/models/querysets/#select-for-update) описує блокування рядків через `select_for_update()` до кінця транзакції; для цього рішення використовується PostgreSQL. Правила читання порожніх даних: прогрес 0%, kcal 0 лише за відсутності завершень; за наявності завершення без оцінки — `null`/позначка неповноти за BR-012.

### Пріоритети добору `ProgramTemplate` (`Strategy`)

До кандидатів входять лише опубліковані шаблони з **точним** збігом `fitness_goal` та `experience_level`; між цілями й рівнями автоматичного fallback немає. Кандидатів упорядковують послідовно: (1) найменше `abs(template.workouts_per_week - profile.workouts_per_week)`; (2) за рівної відстані — менша частота шаблону; (3) за подальшої рівності — критерій стратегії цілі з таблиці; (4) остаточна нічия — менший `ProgramTemplate.id`. Частки обчислюють із кількості входжень вправ відповідної категорії в шаблоні; шаблон має принаймні одну вправу. Добір є детермінованим, без AI/ML. Це погоджений порядок BR-005 для MVP.

| Стратегія | Критерій після спільних пріоритетів |
|---|---|
| `WeightLossSelectionStrategy` | Максимальна частка вправ `cardio`. |
| `MuscleGainSelectionStrategy` | Максимальна частка вправ `strength`. |
| `MaintenanceSelectionStrategy` | Найменша різниця між найбільшою та найменшою частками `cardio`, `strength`, `yoga` (найрівномірніший склад). |

За відсутності кандидата User отримує явне повідомлення, і `UserProgram` не створюється. Різниця в частоті є пріоритетнішою за склад вправ; склад лише розв'язує нічию між шаблонами однакової близькості. Цей порядок свідомо зберігає регулярність занять як пріоритет MVP.

Початкова команда наповнення каталогу має створити щонайменше **два шаблони для кожної з трьох цілей**. У кожній парі однакові мета, рівень і `workouts_per_week`, але різний склад вправ, щоб саме критерій відповідної `Strategy` визначав переможця. Перевірка добору для кожної цілі має продемонструвати різний результат при зміні складу шаблонів; окрема перевірка підтверджує, що точніша частота переважає вигідніший склад.
