# Дизайн-система Nordic Vitality

Цей документ є канонічною візуальною специфікацією React-клієнта. Він задає палітру й стабільні ролі, але не підтверджує, що будь-який окремий екран або дія вже реалізовані. Інтерфейсна мова — українська. Бізнес-стани й доступ до даних визначають API-контракт та сервер, а не макет Stitch.

## Джерела й пріоритет

1. Затверджена палітра з опису завдання має пріоритет для бренду: `#173C35`, `#27866C`, `#C5EA78`, `#182B26`; гарнітура — Manrope.
2. Усі три експортовані `nordic_vitality/DESIGN.md` однакові між собою, але їхній YAML не збігається з prose. YAML дає палітру на кшталт `#002620`, `#006B54`, `#E8FEF6`, `#0C1F1A`; prose повторює чотири затверджені brand colors і додає поверхні та статуси.
3. HTML-експорти підтверджують використання темної дії `#002620`, `#006B54`, світлих mint surfaces, Manrope та непомітних зелених тіней. Вони лишаються джерелом семантичних токенів, а не замінюють бренд.
4. Три файли `DESIGN.md` однакові; це не означає, що кожен експортований екран схвалений. Реєстрація, вхід і оболонка потребують перевірки у справжньому застосунку.

Змінні визначено у [tokens.css](../../frontend/src/styles/tokens.css), базове глобальне оформлення — у [style.css](../../frontend/src/style.css). Компоненти мають використовувати семантичні змінні, а не власні копії палітри.

## Реалізація у frontend

`tokens.css` залишається єдиним джерелом значень Nordic Vitality. Глобальний `style.css` імпортує Tailwind CSS v4 та токени, а блок `@theme inline` пов'язує семантичні змінні з утилітами Tailwind (`bg-background`, `text-foreground`, `bg-primary`, `border-outline`, `ring-ring` тощо). Назви aliases відрізняються від вихідних змінних, щоб не створити циклічні CSS-посилання. Нові сторінки використовують ці ролі, а не локальні HEX-палітри.

Tailwind підключено офіційним `@tailwindcss/vite` у наявному Vite-застосунку. `components.json` налаштовує shadcn/ui з Base UI (`base-nova`) і TypeScript-аліасом `@/`; потрібні примітиви розміщуються лише у `src/components/ui/` та адаптуються до чинних публічних props. shadcn/ui тут є джерелом компонентного коду, а не окремою темою чи паралельною бібліотекою компонентів. SCSS і Tailwind CDN у застосунку не використовуються. React Router 7 і спільний API-клієнт із Django session/CSRF зберігаються.

Для повідомлення про будь-який статус завжди показувати текст або піктограму з доступною назвою; колір сам по собі не передає значення. Лаймовий акцент — декоративний/progress, не зелений статус успіху. Помаранчевий `#F4A261` — акцент енерговитрат/графіків, а не попередження.

### Контраст

Ціль — WCAG 2.2 AA: звичайний текст не нижче 4.5:1, великий текст не нижче 3:1, важливі межі компонентів і графічні стани не нижче 3:1 до суміжного кольору. Виміряні значення для ключових суцільних кольорів: `#182B26` на білому — 14.87:1; `#414846` на білому — 9.37:1; білий на `#002620` — 16.18:1; білий на `#006B54` — 6.50:1; білий на `#BA1A1A` — 6.46:1. Білий на brand secondary `#27866C` — 4.46:1, тож не використовувати цю пару для звичайного тексту; застосовувати темну дію або іншу доступну комбінацію. Текст `#687A73` на `#F6F8F5` близько 4.26:1, тому token muted використовує темніший `#414846`.

Перевіряти реальні кольорові пари після прозорості, hover, disabled і накладання шарів. Не знижувати контраст заради точного копіювання макета.

## Типографіка

Базова гарнітура — Manrope. `style.css` завантажує потрібні ваги 400–800 із Google Fonts CSS із `display=swap`; шрифт не вважається встановленим на клієнті. Це зовнішня runtime-залежність: за недоступності Google Fonts браузер використовує `"Segoe UI", sans-serif`, потім системний sans-serif. Для офлайн або середовища із забороненим зовнішнім шрифтом треба додати ліцензовані локальні font assets і замінити імпорт; локальних Manrope файлів у репозиторії зараз немає. Для україномовного тексту перевіряти кириличні знаки, цифри та перенесення рядків. Імпорт не покладається на Tailwind CDN.

| Стиль | Розмір / інтерліньяж | Вага | Використання |
| --- | --- | --- | --- |
| Display | 56 / 64 px | 800 | Рідкісне велике промо або ключовий показник |
| Заголовок сторінки | 36 / 44 px; mobile 28 / 36 px | 700 | Назва сторінки |
| Заголовок секції | 24 / 32 px | 700 | Розділ сторінки |
| Заголовок картки | 20 / 28 px | 600 | Заголовок картки або групи |
| Малий заголовок | 18 / 24 px | 600 | Щільні картки |
| Основний текст | 16 / 24 px | 400 | Основний вміст |
| Великий текст | 18 / 28 px | 400 | Вступний або акцентний абзац |
| Малий текст | 14 / 20 px | 400 | Допоміжний вміст |
| Мітка | 14 / 20 px | 600 | Label та керування |
| Компактна мітка | 12 / 16 px | 600 | Короткі бейджі, заголовки даних |
| Підпис | 12 / 16 px | 500 | Метадані та підписи графіків |

Відповідні змінні типографіки зберігають ці розміри та інтерліньяжі. Ваги доступні як `--font-weight-regular/medium/semibold/bold/extrabold`; для заголовків і міток є стримані `--letter-spacing-heading` та `--letter-spacing-label`. Заголовкам дозволено щільніший негативний tracking із DESIGN.md; довгий український текст не стискати. Числа в аналітиці можуть використовувати `font-variant-numeric: tabular-nums`.

## Відступи, радіуси й тіні

Відступи спираються на 8px ритм із половинними кроками 4px: `--space-1` = 4px, `--space-2` = 8px, `--space-3` = 12px, `--space-4` = 16px, `--space-6` = 24px, `--space-8` = 32px. `--space-5`, `--space-10`, `--space-12` призначені для послідовних проміжних і великих кроків.

| Токен | Значення | Типове використання |
| --- | --- | --- |
| `--radius-sm` | 4px | Компактні теги й дрібні елементи |
| `--radius-control` | 10px | Поля й кнопки |
| `--radius-md` | 12px | Менші контейнери |
| `--radius-card` | 16px | Картки |
| `--radius-lg` | 24px | Великі картки/панелі |
| `--radius-pill` | 9999px | Пілюлі та круглі аватари |

Застосовувати `--shadow-card` для ледь піднятої картки, `--shadow-card-hover` — лише якщо картка справді інтерактивна, `--shadow-overlay` — для діалогу. Поверхні також мають тонку межу; тінь не замінює її.

## Макет і адаптивність

Постійна оболонка використовує бічну панель шириною 260px (Stitch shell — 256px), верхню панель висотою 72px та нижню мобільну навігацію висотою 56px. Контент обмежений 1440px і має зовнішні поля 32px на широкому desktop. Сітка: 12 колонок із gutter 24px на desktop; 8 колонок із gutter 16px на tablet; одна або дві колонки на вузьких екранах із полями 16px. Картки всередині секції зазвичай розділяє 16px, більші секції — 24px.

Спільні орієнтири breakpoint-ів (ширина viewport):

| Межа | Адаптація |
| --- | --- |
| 640px | Перехід від вузького одноколонкового компонування до компактних 2 колонок, якщо вміст дозволяє |
| 768px | Tablet-сітка на 8 колонок; навігація ще може бути згорнута |
| 1024px | Вибір між компактною навігацією та повною бічною панеллю залежно від доступної ширини контенту |
| 1280px | Повна desktop-оболонка й 12-колонкова сітка |

Ці пороги нормалізують загальну поведінку, а не є точними вимірами Stitch: DESIGN.md описує мобільні/tablet/desktop макети, проте не фіксує числових breakpoint-ів. Підтвердити їх на реальних сторінках та ширинах 320px, 375px, 768px, 1024px і 1440px. Не ховати потрібні дії та текст при зміні навігації. Desktop sidebar має ставати drawer або bottom nav на вузькому екрані; не стискати її до непрацездатної смуги.

## Стани компонентів

Кожен повторно використовуваний інтерактивний компонент має визначати доречні стани:

- **Default** — базова поверхня, межа й контрастний текст.
- **Hover** — колір поверхні або межі змінюється; не покладатися лише на колір.
- **Focus-visible** — чітке кільце 3px із відступом; фокус не прибирати.
- **Active / selected** — відрізняється форма/заливка/піктограма або текстом стану.
- **Disabled** — неактивна дія, доступне пояснення за потреби; disabled-колір не використовувати для важливої інформації.
- **Loading** — показувати зайнятість і доступне ім'я; не втрачати введені дані.
- **Error / success** — текстове повідомлення та семантичний знак, за потреби `aria-live`; не вигадувати успіх до відповіді сервера.

## Доступність

Ціль — WCAG 2.2 AA. Використовувати семантичні елементи HTML, справжні `button` і посилання, постійні label для полів, зв'язок підказок/помилок через `aria-describedby`, клавіатурний порядок без пасток та видимий focus-visible. Перевіряти контраст звичайного й великого тексту, меж інтерактивних елементів, chart legends та графіків. Не передавати помилку, вибір або прогрес одним лише кольором.

Діалоги мають мати доступну назву, керувати фокусом, закриватися клавіатурою, якщо це дозволяє дія, і повертати фокус до ініціатора. Для оновлень стану застосовувати відповідну live region без надмірного оголошення. Підтримувати `prefers-reduced-motion`; глобальне правило в `style.css` прибирає тривалі анімації для цієї системної переваги. Перевіряти з клавіатурою, screen reader і touch viewport.

## Використання токенів

```css
.example-card {
  padding: var(--space-6);
  border: 1px solid var(--color-border);
  border-radius: var(--radius-card);
  color: var(--color-text-primary);
  background: var(--color-surface);
  box-shadow: var(--shadow-card);
}

.example-card__title {
  margin: 0;
  font-size: var(--font-size-title-medium);
  line-height: var(--line-height-title-medium);
}
```

Використовуйте семантичні назви ролей, наприклад `--color-action-primary`, а не конкретний компонентний колір на кшталт `--login-button-green`. Рідкісне унікальне значення дозволене лише з поясненням у локальному стилі й не має дублювати наявний токен.

## Реєстр майбутніх спільних елементів

Мінімальний набір для першого набору функцій: `AppShell` з sidebar/top bar/mobile navigation, `PageHeader`, `ContentContainer`, `Button`, `Card`, `Badge`, `Field` із типізованими input/select/checkbox варіантами, `Alert`, `EmptyState`, `LoadingState`, `Modal`/`ConfirmDialog` і пагінація. Доменні картки або графіки додаються лише коли реальні поля та поведінка повторюються між екранами. Компоненти відповідають за власні розміри, стани й композицію; цей документ не вимагає створювати всі перераховані елементи одразу.

Візуальні опори Stitch: D04/M01 та D06 — публічні форми; D00/D03/A04/C06 — оболонка; D05/D10/A04 — повторювані картки; A02/A09/C03 — діалоги; D09/A11 — графіки. HTML-файли є прототипами з CDN Tailwind, inline-стилями та демо-даними; переносити до застосунку лише перевірену структуру й дизайн, а не їхні скрипти, handlers, фіктивні значення чи непідтверджену поведінку.
