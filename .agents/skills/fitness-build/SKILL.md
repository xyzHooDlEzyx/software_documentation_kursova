# Наскрізний зріз

## Принцип

Один зріз має один користувацький результат, конкретні `FR`/`UC`/`BR` і один
або малу зв’язану групу REST ID. Не об’єднуй незалежні фази, масовий refactor і
нову поведінку в одну зміну.

Локальний `docs/implementation/implementation-plan.md` можна прочитати для
dependency order, phase і DoD. Він навмисно untracked: не додавай посилання на
нього до tracked docs або `README.md`. `docs/PLAN_VARIANT_4.md` не використовуй.

## Порядок роботи

1. **Вимоги — `fitness-requirements`.** Визнач ID, статуси, acceptance criteria і
   gate. На `OPEN`/`CONFLICT` зупинись і попроси рішення власника.
2. **Модель — `fitness-model`.** Перевір Domain Model, Use Case і GoF. Змінюй
   діаграми лише коли зріз справді змінює модель.
3. **База — `fitness-database`.** Спершу ERD, потім ORM, пряма міграція,
   тести міграції й seed за потреби.
4. **Backend — `fitness-backend`.** Реалізуй serializer/service/selector/view,
   permissions, error envelope, транзакцію та PostgreSQL-тести.
5. **Admin — `fitness-admin`.** Додай адміністративний канал лише якщо він є
   частиною вимоги; permission migration й service guards обов’язкові.
6. **Frontend — `fitness-frontend`.** Додай DTO, сторінку, route/nav, стани й тести
   лише поверх реалізованого API.
7. **Перевірка — `fitness-verify`.** Запусти релевантні вузькі тести, повний
   набір перевірок і ручний E2E пропорційно ризику.
8. **Документація.** Синхронізуй лише зачеплені канонічні документи й актуальні
   розділи `README.md`.
9. **Коміт — `fitness-repository`.** Якщо користувач дозволив коміт, створи один
   або кілька тематичних комітів з описовими English messages без AI attribution.

Не завантажуй усі навички механічно: на кожному кроці відкрий відповідну, якщо
зріз зачіпає цей шар. Для виправлення лише backend пропусти незмінені DB/Admin/UI,
але все одно простеж вимогу й перевір regression.

## Критерії завершення

Slice завершено, коли:

- результат простежується до канонічних ID, а статуси не підвищено мовчки;
- Domain Model/ERD/REST/UML узгоджені там, де змінились;
- схема має пряму міграцію і перевірене оновлення, якщо дані змінено;
- шлях запису атомарний, обмежений власником і повертає спільний error envelope;
- admin permissions і guards перевірено, якщо додано адміністративну поверхню;
- UI використовує реальний API та має loading/empty/error/success;
- backend і frontend тести доводять критерії приймання й негативні межі;
- повний доступний набір перевірок пройдено, а `NOT RUN` чесно пояснено;
- `README.md` описує фактично реалізований стан і відтворюваний запуск;
- немає секретів, demo claims або запланованих функцій, виданих за готові.

## Документація та статус

Оновлюй `docs/analysis/`, `docs/architecture/` і документи маршрутів/дизайну лише
за реальною зміною контракту. Не створюй нову систему статусів. Файли в
`docs/review/` або окремий файл статусу оновлюй лише якщо такий артефакт уже існує
для поточного огляду чи процесу і запит прямо передбачає його підтримку.

Не перетворюй `docs/review/senior-review-2026-11-14.md` на живий changelog: це
датований review, хоча його відкриті рішення слід враховувати.

## Контроль масштабу

Перед стартом назви ID в обсязі роботи, шари й файли; після реалізації переліч
фактичні відхилення. Якщо зріз потребує нового бізнес-рішення, зовнішньої
інтеграції або зміни каналу адмін-звітів, зупинись і попроси власника, а не
розширюй обсяг.
