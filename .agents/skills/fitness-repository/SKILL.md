# Репозиторій

## Перед змінами

Переглянь `git status --short` і збережи всі не пов’язані зміни власника. Не
використовуй destructive reset/checkout і не включай сторонні файли до коміту.
Коміт створюй лише якщо користувач це дозволив.

`README.md` є публічним джерелом відтворюваного запуску й реалізованого стану.
Канонічні вимоги та архітектура живуть у `docs/analysis/` і
`docs/architecture/`; не перенось їхні бізнес-правила, переліки полів чи таблицю
REST-операцій у README.

## Тематичні коміти

Групуй зміни за одним наскрізним зрізом або однією самодостатньою технічною
причиною. Відокремлюй велике оновлення документації та діаграм від продуктового
коду, якщо їх можна перевірити незалежно. Не змішуй форматування всього
репозиторію з функцією.

Повідомлення пиши описовою англійською в наказовому способі, за результатом
зрізу, а не `Update files` чи номером фази. Ніколи не додавай
`Co-Authored-By: Claude`, іншу AI attribution у commit/PR або згадку про
генерацію агентом: це правило власника.

Перед комітом переглянь staged diff і запусти `fitness-verify` у пропорційному
обсязі. У handoff наведи commit hash лише якщо commit фактично створено.

## README після зрізу

Оновлюй лише розділи, яких торкнувся реалізований стан:

- `Поточний стан` — що справді працює та що ще не реалізовано;
- `Передумови та версії` — лише після зміни середовища виконання або залежності;
- `Запуск з нуля` — змінні середовища, PostgreSQL, міграції, seed, admin і процеси;
- `REST API (реалізовані операції)` — лише фактично доступні REST ID;
- `Перевірки` — точні підтримувані команди;
- `Production` — тільки перевірена production-конфігурація;
- `Діагностика` — відтворювані типові відмови.

Не оголошуй фазу або функцію завершеною лише через додану міграцію чи backend,
якщо acceptance criteria вимагають UI/Admin/доказ. Команди README перевіряй у
чистій shell session із завантаженим `.env`.

## Ігноровані навмисно файли

`docs/PLAN_VARIANT_4.md` та `docs/implementation/implementation-plan.md`
навмисно не входять до Git. Навички в `.agents/skills/` відстежуються в Git:
зміни в них комітуй окремим тематичним комітом.
Історичний `docs/PLAN_VARIANT_4.md` не використовуй. Локальний implementation
plan можна читати для phase order/DoD, але не додавай на нього посилання з
tracked docs або `README.md` і не force-add його.

Не змінюй `.gitignore`, щоб випадково опублікувати ці файли, без окремого
рішення власника.

## Secrets і середовище

`.env` ніколи не коміть. Публічним шаблоном є `.env.example`: там лишаються
безпечні placeholders і назви змінних, але не реальні паролі, секретні ключі,
токени чи облікові дані тестових користувачів.

Перед додаванням до індексу перевір diff на облікові дані, reset URLs, cookies,
дампи БД, локальні знімки екрана з приватними даними та артефакти редактора або
середовища виконання. Не
публікуй вивід команди, якщо він містить secret.

Файли фіксації залежностей оновлюй разом із маніфестом лише коли залежність
справді змінено. Не додавай бібліотеку або інфраструктуру лише тому, що її
згадував старий план: потребу має доводити поточний зріз.

## Готовність до випуску

Перевір, що `compose.yaml` піднімає лише потрібний service `db`, налаштування за
`README.md` доходить до migrate, `seed_catalog`, `createsuperuser` і двох dev
процесів, а `.env.example` узгоджений із settings. Для тестів роль PostgreSQL має
`CREATEDB`; не приховуй цю передумову.

Фінальна передача містить обсяг, змінені канонічні документи, фактичні перевірки,
невиконані перевірки, відомі обмеження і наступний готовий за залежностями зріз.
