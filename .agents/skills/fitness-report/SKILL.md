# Звіт курсової роботи

## Джерело вимог

Прочитай §3 `docs/kursova_DPZSP.pdf` і звір варіант 4 у §2. Не використовуй
`docs/PLAN_VARIANT_4.md` як джерело. Функції й поведінку простежуй до
`docs/analysis/requirements.md`, `docs/analysis/business-rules.md` та фактичного
коду; не копіюй у звіт непогоджені `PROPOSED` як реалізовані рішення.

## Каркас за §3

Покрий усі дев’ять пунктів методички такими репозиторними доказами:

1. Титульний лист — оформлення навчального закладу й дані роботи.
2. Завдання — варіант 4 «Фітнес-додаток» без доданих вигаданих вимог.
3. Use Case diagram — `docs/diagrams/use-case-diagram.svg` і пояснення з
   `docs/analysis/use-case-diagram.md`.
4. Class diagram — актуальний export із `docs/diagrams/class-diagram.drawio`,
   пояснення логіки, кольорова легенда GoF за Додатком В.
5. Інші структури — лише корисні ERD/sequence/architecture views із
   `docs/architecture/`, що пояснюють реалізацію.
6. Стек — версії з `README.md`, `backend/requirements.txt`,
   `backend/pyproject.toml` і `frontend/package.json`.
7. Код — пояснення основних фактичних modules, components, classes та їхньої
   відповідальності.
8. Результати — якісні знімки UI, основних сценаріїв, Django Admin і БД.
9. GitHub і запуск — посилання на repository та актуальний `README.md` з
   відтворюваними командами.

Не дублюй у тексті повні переліки полів, таблиці операцій або бізнес-правила.
Посилайся на `FR`/`UC`/`BR`/REST ID і пояснюй лише рішення, потрібне читачеві.

## Діаграми

Use Case SVG генерується через
`docs/diagrams/tools/render_use_case_svg.py`; його не редагують вручну. Class
diagram має стати однією узгодженою моделлю з GoF legend. Наявні class PNG
застарілі, а кольори сторінок 01 і 04 мають конфлікт значень; перед включенням у
звіт діаграму треба виправити й повторно експортувати за `fitness-model`.

## Пояснення GoF

Описуй учасників, взаємодію, проблему й доказ тестами, а не визначення з
підручника:

- реалізований `Strategy`: `backend/planning/strategies.py` і
  `ProgramSelectionService` у `backend/planning/services.py`;
- `Observer` спроєктовано, але його учасники заплановано для фаз 6–7 і ще не
  реалізовано;
- `Template Method` спроєктовано, але заплановані процесори ще не реалізовано.

До реалізації останніх двох чесно позначай їх як проєктні, не як завершений код.
`Factory Method`, `State` і `Command` із
`docs/architecture/additional-gof-proposals.md` не включай до переліку
використаних патернів без реальної реалізації.

## Знімки екрана

Знімай стабільне локальне середовище без облікових даних, токенів, посилань для
відновлення пароля або приватних даних. Потрібні лише знімки, що доводять
заявлені результати:

- основні реалізовані user flows у desktop і доречному mobile viewport;
- loading/empty/error або validation state, якщо він пояснюється у звіті;
- permissions Django Admin і безпечне для домену редагування;
- таблиці/зв’язки PostgreSQL або query result без секретів;
- результати основних функцій і трьох звітів лише після їх реалізації.

Кожен screenshot підпиши: сценарій, пов’язаний ID і що саме він доводить. Не
використовуй Stitch prototype як screenshot готового застосунку.

## Чесність стану

Не вигадуй deployment, endpoint, test result, class або UI. Нереалізовані
`execution`/`engagement`, невстановлений `reporting`, заплановані соціальні
функції та звіти описуй у розділі обмежень як «не реалізовано», доки код і
перевірка не доводять інше. Відкритий канал `R02`/`R03` також не вирішуй у звіті.

## Випуск документа

Сам файл звіту створюй лише на окремий запит власника. Для DOCX застосуй навичку
роботи з DOCX, доступну в поточному середовищі агента, або `python-docx`. Потім
відрендери чи конвертуй документ у PDF і візуально перевір кожну сторінку. Перед
фінальною видачею звір зміст із поточним Git state, онови зміст/нумерацію,
перевір captions, читабельність diagrams і відсутність артефактів чату.
